# Paper Party Expansion: SOS & Connect Four — Implementation Plan

**Plan ID**: 1779706333960-curious-tiger  
**Goal**: Add two new server-authoritative, highly playable, mobile-first multiplayer games — **SOS** (with custom board sizes) and **Connect Four** (classic 6×7) — to the existing PaperParty monorepo. Strictly adhere to current architecture (JS, CommonJS in api/, no TypeScript/Zustand, Context + per-game state, shared sketch/paper UI components, BaseManager patterns, Mocha + Vitest + Playwright E2E). Prioritize smooth low-latency multiplayer, satisfying physics/animations/combos, sounds, spectator support, and TDD. Leverage and extend shared components from the start to minimize future duplication.

**Recorded User Decisions** (from clarification):

- Routes & prefixes: `/sos` + `sos_` events; `/connect4` + `c4_` events.
- Component files: `pro/src/sos/SOSGame.jsx` and `pro/src/connect4/Connect4Game.jsx`.
- Add `framer-motion` to `pro/` for premium falling-disc physics, combo line traces, win highlights, and future-proofing (critical for "addictive" per expansion goals).
- Spectator support: **Yes** — allow observers to join full (2-player) rooms as read-only viewers with live updates; no move capability; UI indicates spectating.
- SOS boards: **Custom sizes supported** (like DAB modes) — 4×4 to 8×8 (clamped, square only). Recommend presets: 5×5 (quick), 6×6 (balanced), 7×7 (deeper). C4 fixed at classic 6 rows × 7 cols.
- Testing: Full coverage — unit (game logic), integration (socket flows), E2E Playwright smoke (create/join/play/win/restart/spectate/reconnect) for both games.

## 2. Current Architecture Constraints & Alignment

**Server (api/)**:

- CommonJS, `require`, `module.exports`.
- All managers: `class XxxManager extends BaseManager { gamePrefix = 'xxx'; handleConnection(socket) { socket.on(`${this.gamePrefix}\_...`, ...) } }`
- Events: createRoom, joinRoom, makeMove / startGame / restartGame / leaveRoom / reconnect / requestRoomInfo / disconnect.
- State in `this.rooms: Map<roomId, Room>`; Room has `id, players[], gameState ('waiting'|'playing'|'ended'|'paused'), currentTurn, ...gameSpecific`.
- Error: always `socket.emit('xxx_alert', {icon, title, text})`.
- Reconnect/leave/pause use Base helpers + per-game overrides (some duplication still exists).
- HTTP: /stats must include new games; /cleanup and shutdown must handle new managers.
- Tests: `api/test/xxx.test.js` (Mocha + socket.io-client @ port 4001); NODE_ENV=test skips listen.

**Frontend (pro/)**:

- ES modules, React 18 + Vite, Tailwind v4 + custom `.sketch-card`, `.bg-paper`, `.font-sketch`, `.paper-font`, etc.
- Imports: React → external (react-router, lucide, use-sound, framer-motion after add, canvas-confetti, sweetalert2) → internal (relative).
- Single socket from `GameContext` (playerName, roomId, socket, setRoomId, clearRoomId).
- Per-game pages manage local state + socket listeners (cleanup in useEffect).
- Reconnect: `sessionStorage.getItem('sos_reconnect')` etc. + emit on mount.
- Shared UI (import from `../components/ui`): GameLayout (wraps), RoomLobby (for explicit-start + waiting + host start), MatchReport (post-game), AvatarSelector, LeaveButton, TurnIndicator, Sketch\* primitives, sketchPopupClass for Swal.
- Sounds: `use-sound('/sounds/xxx.mp3')`; existing assets: move/pop/turn/win.mp3 in `public/sounds/`.
- Landing: hard-coded GameCard grid + custom SVG icons in PaperPartyLanding.jsx; add two new cards (remove from "Coming Soon").
- Routing: App.jsx + BrowserRouter.
- Tests: Vitest + RTL; mocks for socket/sound/confetti/swal; per-game `Xxx.test.jsx`.
- E2E: Playwright in `e2e/` (per-game `*.spec.js` + `helpers.js` with navigate/create/join helpers); `e2e/playwright.config.js`.

**Deviations from request's "suggested" structure**:

- No `src/games/sos/`, no `server/` rename, no TS, no Zustand, no new sockets/ or rooms/ folders.
- Keep flat-ish per-game folders (like uttt/components/ for complex bits); main page at root of its dir.
- Add framer-motion (justified by UX goals + user confirmation).

**Reusable wins for new games**:

- New games will be the first to fully adopt RoomLobby + explicit start (modeling future unification).
- Spectator logic can be partially hoisted to BaseManager in a later polish if desired.
- Generic board + line-highlight primitives (SVG or divs + framer) can be extracted.

## 3. Game Specifications (Adapted to Current Stack)

### SOS

- **Board**: Square, configurable at create (4–8, presets 5/6/7). Cells: `null | 'S' | 'O'`.
- **Players**: 2 (plus any number of spectators).
- **Flow**: Host creates (picks size) → waiting lobby (RoomLobby) → others join as Player (fills 2nd slot) or Spectator → Host starts when ≥2 players → alternate turns (or extra on score) → place S/O in empty cell.
- **Scoring**: +1 per SOS formed (horizontal/vertical/diagonal). One placement can score 2+ (combo). Scorer gets extra turn.
- **End**: Board full → highest score wins (or draw).
- **Events** (all `sos_*`): createRoom({playerName, size}), joinRoom({roomId, playerName, asSpectator?}), startGame({roomId}), makeMove({roomId, row, col, value}), restartGame, leaveRoom, reconnect, requestRoomInfo.
- **State shape** (room):
  ```js
  {
    id, players: [{id, name, connected, isHost?}], spectators: [{id, name, connected}],
    size: 6, board: string[][], scores: {p1:0, p2:0}, currentTurn: socketId | null,
    gameState: 'waiting'|'playing'|'ended', moveHistory: [...], formedPatterns?: [...] // for highlights
  }
  ```
- **Key server logic**: validate turn/empty/valid symbol; place; scan 8 dirs from placed cell (or full cheap scan) for all new `S O S` (center or edge); award per pattern; decide extra turn vs switch; broadcast move + scores + formed (for anim) or full roomInfo.

### Connect Four (C4)

- **Board**: Fixed 6 rows × 7 cols. Cells: `null | 'red' | 'yellow'`.
- **Players**: 2 (red=p1, yellow=p2) + spectators.
- **Flow**: Host creates → waiting → p2 joins or spectate → host starts (or auto if we decide) → drop disc into column (gravity to lowest empty) → check win (4 connected horiz/vert/diag).
- **End**: 4-in-a-row (win) or board full (draw).
- **Events**: `c4_*` (createRoom, joinRoom, startGame, makeMove({roomId, column}), etc.).
- **State**: `board: Cell[][]` (row 0 = top), currentTurn, winner?, lastMove? (for optimized check + anim origin).
- **Win detection**: Only rays from last placed disc (4 directions, count streaks) — O(1) per move.
- **Frontend critical**: Column hover/active highlight + transparent preview disc (framer); falling animation with slight bounce (framer spring + perhaps velocity); win line glow + connect trace; column tap anywhere drops.

**Shared multiplayer** (both games):

- Spectators: receive all roomInfo/move broadcasts; see live board + scores/turn; "Spectating" UI badge; no emit moves; can leave cleanly.
- Reactions (future stretch): quick emoji bar (🔥 etc.) broadcast to room.
- Reconnect: works for players _and_ spectators (restore role + state).
- Move history stored for potential replay (in-memory only).

## 4. Backend Implementation Details

### New Files

- `api/game-logic/sos.js` (extends Base, ~300–400 LOC with detection)
- `api/game-logic/connect4.js` (extends Base, win-check optimized)
- `api/test/sos.test.js`
- `api/test/connect4.test.js`
- (Optional) extend `api/test/integration.test.js` for cross-game + spectator flows.

### Required Changes

- `api/index.js`:
  - Add requires + instantiate `sosManager`, `connect4Manager`.
  - Register both in `io.on('connection')`.
  - Add to `/stats`, cleanup loop, shutdown loop, export.
- (Minor) `BaseManager.js` — optional helpers if useful:
  - `addSpectator(room, socket, name)`, `removeSpectator`, `isSpectator`.
  - Or implement purely in the two new managers (simpler for scope).

### SOS Engine TDD Order (Mocha style, mirror existing)

1. Board init (create with size, empty 2D, scores 0, waiting state).
2. Move validation (turn, empty cell, valid 'S'/'O', size bounds).
3. SOS detection (horiz/vert/diag; multiple from one cell; patterns where placed cell is edge or center).
4. Scoring + turn logic ( +N points, extra turn if scored >0 else switch; emit formed patterns).
5. Game end (full board → winner by score or draw).
6. Full flows: create (size), join (player vs spectator), start, reconnect (both roles), leave/pause, restart.
7. Spectator isolation (cannot move; still receives updates).

### C4 Engine TDD Order

1. 6×7 board creation/empty.
2. Gravity drop (find lowest row in col; reject full col).
3. Turn alternation + validation.
4. Win detection (all 4 dirs from last move only; horiz/vert/diagL/diagR).
5. Draw on full board.
6. Full socket flows + spectator + reconnect.

**Event contract (use template literals like dab)**:

```js
socket.on(`${this.gamePrefix}_createRoom`, ...)
socket.on(`${this.gamePrefix}_makeMove`, ...)
socket.on(`${this.gamePrefix}_startGame`, ...)  // for both
// etc.
```

Emits: `_roomInfo`, `_gameStarted`, `_moveMade` (or game-specific payload with new board/score/turn/winner/line/patterns), `_alert`, `_playerLeft`, `_gamePaused`, `_gameRestarted`.

Early returns on invalid; never throw.

## 9. Risks & Mitigations

- **Risk**: Spectator role + custom SOS size adds state surface / edge cases (join as spec after p2 full, size in all paths, start validation).  
  **Mitigation**: TDD the matrix early; keep spectators simple list parallel to players; clamp size aggressively; one vertical slice per game before full spectator.

- **Risk**: Framer falling animation feels "dead" or janky on low-end mobile / causes layout shift.  
  **Mitigation**: Use `layout` + spring with tuned values; test on real devices early in Phase 5; provide `prefers-reduced-motion` fallback (instant place); profile with React DevTools.

- **Risk**: Dynamic grid + 8×8 SOS cramped or slow on small phones.  
  **Mitigation**: Max 7×7 practical; use CSS `minmax(32px, 1fr)` + touch feedback; 4×4/5×5 as quick-play defaults.

- **Risk**: Adding dep + new patterns slightly increases bundle (framer ~ few KB gz).  
  **Mitigation**: Tree-shake; only import { motion, AnimatePresence } in game files; acceptable for UX goals.

- **Risk**: Unification debt grows (new games perfect, old still duplicated).  
  **Mitigation**: Document in AGENTS.md "New games (SOS/C4) use RoomLobby + explicit start + spectators as the target pattern"; small polish PRs later cheap.

- **Risk**: Sounds — licensing / file size.  
  **Mitigation**: Use short public-domain or self-generated tones (or existing + volume variants); compress; document sources in PR.
