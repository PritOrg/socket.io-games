### 1.3 Extract `useReconnection` hook

**Path:** `pro/src/hooks/useReconnection.js` (new)

Standardize across all six games. The pattern today is:

- Check `sessionStorage` for `<prefix>_reconnect`
- If found and not yet attempted → emit `<prefix>_reconnect`
- On `<prefix>_roomInfo` → restore state + write new sessionStorage entry
- Clear on game end/restart/leave
- Bingo/TTT/UTTT lack `reconnectAttempted` ref

```js
function useReconnection({ socket, gamePrefix, roomId, onRoomInfo, onRestore }) {
  const attemptedRef = useRef(false);
  useEffect(() => {
    if (!socket) return;
    const key = `${gamePrefix}_reconnect`;
    const saved = sessionStorage.getItem(key);
    if (saved && !attemptedRef.current) {
      attemptedRef.current = true;
      try {
        const { roomId: savedRoomId, playerId } = JSON.parse(saved);
        socket.emit(`${gamePrefix}_reconnect`, { roomId: savedRoomId, playerId });
      } catch {
        /* ignore corrupt data */
      }
    }
    // ...
  }, [socket, gamePrefix, roomId, onRoomInfo, onRestore]);
}
```

**Will also expose:** `clearReconnect()` helper to replace individual `sessionStorage.removeItem` calls.

### 1.4 Extract `useSocketListeners` hook

**Path:** `pro/src/hooks/useSocketListeners.js` (new)

Replace the monolithic `useEffect(() => { socket.on(...) ... return () => socket.off(...) }, [socket, ...])` blocks. Each game passes a map of event → handler.

```js
function useSocketListeners(socket, listeners, deps = []) {
  useEffect(() => {
    if (!socket) return;
    Object.entries(listeners).forEach(([event, handler]) => {
      socket.on(event, handler);
    });
    return () => {
      Object.entries(listeners).forEach(([event, handler]) => {
        socket.off(event, handler);
      });
    };
  }, [socket, ...deps]);
}
```

# Backend Improvement Plan

## Objective

Align backend event contracts and room-state shapes with the unified frontend plan, closing gaps that currently force per-game frontend workarounds.

---

## B1 — Event Name Consistency: `_gameRestarted`

**Problem:** UTTT emits `uttt_gameStarted` on restart; every other manager emits `<prefix>_gameRestarted`. Frontend handlers must special-case UTTT.

**Fix:** In `api/game-logic/uttt.js`, emit both events on restart (or rename to `gameRestarted`):

- Add `this.io.to(roomId).emit('uttt_gameRestarted')` alongside the existing `uttt_gameStarted` emit
- Frontend: listen for `uttt_gameRestarted` in DAB/TTT/Bingo hook pattern; UTTT frontend can drop the dual-listener

**Scope:** `api/game-logic/uttt.js` + `pro/src/uttt/UTTTGame.jsx` update in migration.

---

## B2 — DAB Undo Payload: Include `requesterName`

**Problem:** `dab_redoRequested` currently emits `{ requesterId }` only. Frontend must look up the name from `players[]` to display "X wants to undo". If the players array hasn't refreshed yet, the name is stale or missing.

**Fix:** In `api/game-logic/dab.js` `requestRedo`, line 255–258:

```js
this.io.to(room.id).emit(`${this.gamePrefix}_redoRequested`, {
  requesterId: socket.id,
  requesterName: room.players[playerIndex].name, // ADD THIS
});
```

Frontend `UndoUI` then has the name directly from the socket event — no lookup needed.

---

## B3 — DAB Timer Cleanup on Leave / Disconnect

**Problem:** If a player leaves (or disconnects) while a redo request is pending, the 15-second `redo_<roomId>` timer keeps running. When it fires, it races with the room being deleted or the request already being null, potentially emitting `dab_redoCancelled` on a dead room.

**Fix:** In `api/game-logic/dab.js`:

1. `leaveRoom`: after splicing/disconnecting, call `this.clearTimer('redo_' + sanitizedRoomId)` and set `room.redoRequest = null`.
2. `handleDisconnect`: inside the per-room loop, also clear the redo timer for that room and null out `redoRequest`.

This prevents orphan timer emissions and keeps state consistent.

---

## B4 — Normalized `roomSettings` on Room Object

**Problem:** DAB stores `mode`, `customRows`, `customCols`, `customPlayers` directly on the room. SOS stores `size`. Other stores store nothing. Frontend's `GameLobby` `customizationSlot` and `gameSettings` need a uniform way to read and display settings.

**Fix:** Add a `settings` object to every room at creation time. Each manager only sets the keys relevant to it.

```js
// In BaseManager createRoom helper OR per-manager createRoom:
room.settings = {
  // DAB:
  mode: mode,            // 'classic' | 'extended' | 'marathon' | 'custom'
  customRows: ...,
  customCols: ...,
  maxPlayers: ...,       // instead of maxPlayers top-level

  // SOS:
  size: ...,             // board size

  // Bingo / TTT / UTTT / Connect4:
  // (empty / defaults)
};
```

**Migration notes:**

- `api/game-logic/dab.js` replace top-level `mode`, `customRows`, `customCols`, `maxPlayers` with `settings` sub-object.
- `api/game-logic/sos.js` add `settings: { size }` to `createRoom`.
- `api/game-logic/bingo.js`, `api/game-logic/tictactoe.js`, `api/game-logic/connect4.js`, `api/game-logic/uttt.js` add `settings: {}` at creation.

Frontend `GameLobby` then reads `room.settings` for `gameSettings` display and `customizationSlot` pre-population (e.g. DAB re-creates the ModeSelector synced to `room.settings.mode`).

`sendRoomInfo` already spreads the room, so `settings` is automatically included — no change needed there.

---

## B5 — Defensive Reconnect: Clear `lastMove` when Relevant Players Disconnect

**Problem (DAB-specific):** If the player who made `lastMove` disconnects, `lastMovePlayerIndex` stays pointing at their slot. On reconnect, `reconnect()` updates `player.id` but the index is still valid. However, `requestRedo` only checks `playerIndex !== lastMoverIndex` — so an opponent who takes that index slot (impossible since indices are fixed by join order) could exploit this. More practically: if ALL players disconnect and rejoin, reconnection order could shift.

**Fix:** In `handleDisconnect` for DAB: if `room.lastMovePlayerIndex !== null` and the disconnected player was `room.players[room.lastMovePlayerIndex]`, reset `room.lastMove = null`, `room.lastMovePlayerIndex = null`, `room.lastClaimedBox = null` and clear the redo timer.

Same logic in `leaveRoom` for active players.

---

## B6 — (Optional) DAB Spectator Support for Full Parity

**Problem:** SOS and Connect4 support `asSpectator` join. DAB only supports players. Frontend `GameLobby`'s `showJoinInput` + `onJoinSubmit` can accommodate spectators if the backend allows it.

**Fix:** Add `asSpectator` boolean to `dab_joinRoom` signature. When true, add to a `room.spectators` array (parallel to `room.players`). Emit spectator list in `sendRoomInfo` via `spectators` field. Frontend shows spectator count in `GameLayout`.

**Defer if:** Spectator support for DAB is not a current user requirement.

---

## B7 — BaseManager Utility: `normalizeRoomForEmit`

**Problem:** Every manager hand-crafts what `sendRoomInfo` emits by spreading the room object. This means new fields added to rooms (like `settings`) are automatically included, but it's not guaranteed. Some managers override `sendRoomInfo` (need to verify).

**Fix:** Add a BaseManager method:

```js
normalizeRoomForEmit(room) {
  const { ...safe } = room;
  return safe;
}
```

All `sendRoomInfo` call sites use this. Makes it explicit that derived/internal fields (if any added later) must be filtered.

Currently not strictly necessary (no internal fields exist), but future-proofs the contract.
